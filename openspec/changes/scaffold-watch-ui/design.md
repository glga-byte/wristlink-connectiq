## Context

See `proposal.md` for motivation and `specs/watch-app-ui/spec.md` for the behavior contract.

The repository currently contains contract material and watch-runtime design references, but no Connect IQ manifest, build configuration, resources, Monkey C source, or tests. The broader runtime described in `docs/design/watch-app-runtime.md` assumes future background delivery, acknowledgements, and durable state; this change must demonstrate only the foreground UI using local session data.

The Paper PNGs are review references rather than runtime assets. The implementation must adapt their hierarchy and dark/action versus light/review visual language to different device display shapes while using current Connect IQ lifecycle, navigation, and input patterns. The locally installed SDK is Connect IQ 9.1.0. The initial product set is Edge 1040 / 1040 Solar and fēnix 7X / Sapphire Solar, whose latest common Connect IQ API level is 5.2.0.

## Goals / Non-Goals

**Goals:**

- Establish a canonical, warning-clean Connect IQ Watch App project with a stable application UUID and no unnecessary permissions.
- Make every specified screen and state reachable through a deterministic local demonstration flow.
- Keep screen rendering, navigation, input handling, and demo state separate enough that future messaging and storage adapters can replace the fixture source without rewriting the UI.
- Validate physical-button and touch operation and both round and rectangular layouts using explicit simulator targets.
- Keep drawing lightweight and avoid parsing, state mutation, or unnecessary allocation in `onUpdate()`.

**Non-Goals:**

- Background services, phone-message registration, contract parsing, acknowledgements, connectivity checks, or any other `Toybox.Communications` behavior.
- `Application.Storage`, settings, migrations, or state that survives an app restart.
- Garmin navigation handoff, waypoint creation, notifications, or a production timer/alarm implementation.
- Pixel-identical reproduction of Paper at every device resolution or broad product support before representative devices have been verified.
- Connect IQ Store metadata, submission packaging, or marketing assets.

## Decisions

### 1. Build a foreground-only Watch App on API level 5.2.0

`WristLinkApp` will extend `Toybox.Application.AppBase`, and `getInitialView()` will return the Home view with its delegate. The manifest will declare a Watch App, set `minApiLevel` to `5.2.0`, omit the Communications permission, and initially list these products:

- `fenix7x`: 280×280 round MIP target representing fēnix 7X, including its Sapphire/Solar hardware configuration; verifies the complete no-touch physical-button path and touch parity.
- `edge1040`: 282×470 rectangular LCD target representing Edge 1040 / 1040 Solar; verifies the tall touch-oriented layout and native control-bar behavior.

The manifest will receive one newly generated application UUID during scaffold implementation. That UUID becomes stable immediately and must not be regenerated by later UI work because the phone projects will eventually reference it.

Garmin lists Edge 1040 at API level 6.0 and fēnix 7X at API level 5.2, making 5.2.0 the highest common baseline. [`AppBase.getInitialView()`](https://developer.garmin.com/connect-iq/api-docs/Toybox/Application/AppBase.html) remains the current lifecycle entry point for returning a view/delegate pair.

Alternatives considered:

- Raising the minimum to 6.0 would exclude fēnix 7X, while lowering it below 5.2 would give up current shared APIs solely for products outside the requested baseline.
- Supporting older products through legacy `Menu` and manual compatibility branches would broaden the matrix before the scaffold is proven and would duplicate menu and input paths.
- Declaring many products up front would imply support that has not been compiled or inspected in the simulator.

The API surface is intentionally limited to current, non-deprecated components available at 5.2.0:

| Purpose | Selected API | Excluded approach |
| --- | --- | --- |
| Application lifecycle | `Application.AppBase`, `getInitialView()` | Deprecated AppBase property/object-store methods |
| Screen composition | `WatchUi.View`, managed layouts, `Text`, `TextArea`, `Button`, `Selectable` | Screen-specific raw event geometry as the primary control system |
| Destination navigation | `WatchUi.Menu2`, `MenuItem`, `Menu2InputDelegate` | Legacy `WatchUi.Menu` and `MenuInputDelegate` |
| Interaction | `BehaviorDelegate`, `SelectableEvent`, `setKeyToSelectableInteraction()` | Separate button and touch action implementations |
| View stack | `WatchUi.pushView()` and `popView()` | Ad hoc global view replacement |

`ActionMenu` is also current at this API level, but it is a contextual-action surface rather than a persistent destination menu, so it is not used here.

### 2. Use one session model and a centralized navigator

The app will construct a `DemoSession` at startup. It owns only in-memory values: the current Inbox state, dummy recent items, dummy saved notes, selected note index, and local action outcomes. A `DemoData` factory will seed the Paper examples (`Trailhead parking`, `Gate code`, and the three-minute `Tea` timer). No view will own its own copy of those fixtures.

An `AppNavigator` will be the only component that creates view/delegate pairs and calls [`WatchUi.pushView()` or `popView()`](https://developer.garmin.com/connect-iq/api-docs/Toybox/WatchUi.html). Delegates translate input into semantic actions and pass them to the navigator/session; they do not contain presentation drawing or future message rules.

The principal stack flow is:

```text
Home (pending) -> Received navigation -> local outcome -> Home (empty)
Home (empty)   -> Recent Items
Home           -> native menu -> Recent Items -> received/detail screen
                            |--> Saved Notes
                            |--> Status
                            `--> About
```

Menu destinations are pushed above the native menu so Back returns to the menu as specified. Back from the menu returns to its invoking screen, and Back from the base Home view follows normal Watch App exit behavior.

Local action behavior is deliberately bounded:

- `Launch` records an in-memory handoff outcome, consumes the dummy pending item, and allows return to the empty Inbox; it never calls Garmin navigation APIs.
- `Later` returns to the pending Inbox without consuming the item.
- `Start timer` changes the received-timer view to a local started outcome; it does not create an alarm or continue after app exit.
- `Save note` routes to the Saved Notes presentation using the same session fixture; it does not write durable state.

Alternatives considered:

- Letting each view mutate global variables would make the demo quick to write but would couple future communications and storage work to UI classes.
- Encoding all navigation inside delegates would repeat view construction and make Back-stack behavior inconsistent.

### 3. Use a resource-defined native `Menu2` for secondary destinations

The destination menu will be defined under `resources/menus/` as a `Menu2` resource with fixed item identifiers and labels from string resources, then loaded through `Rez` and paired with a `Menu2InputDelegate`. It may use the theme, divider, and footer options available within the API 5.2 baseline. Native menu rendering intentionally remains device-specific; the Paper menu snapshot defines content and hierarchy, not a custom imitation of Garmin chrome.

Legacy `WatchUi.Menu` and `MenuInputDelegate` SHALL NOT be included as a fallback. If later product expansion requires a different navigation component, compatibility must be designed and verified as a separate change rather than silently adding an untested branch.

Alternatives considered:

- Programmatic `Menu2` construction is valid, but Garmin recommends resources for fixed menus and the destination set is static.
- A custom full-screen list could match the Paper snapshot more closely, but it would discard native menu behavior and accessibility conventions despite the requirement explicitly calling for a native menu.

### 4. Use custom views with shared layout, theme, and input activation

Each distinct screen will be a lightweight `WatchUi.View` with a managed drawable layout. Current `Text` and `TextArea` drawables will handle static and wrapped content, while `Button`/`Selectable` objects will represent actionable buttons and selectable rows. Common rendering utilities will provide:

- dark action-oriented and light review-oriented themes;
- safe-area-aware vertical layout based on device width and height;
- typography, centered cards, list rows, progress treatment, focus state, and primary/secondary buttons;
- primitive icons and markers drawn through `Graphics`, avoiding packaged Paper bitmaps.

Resolution-aware programmatic drawing is preferred over separate XML layouts for each display shape because the screen set is small, highly centered, and must scale across materially different aspect ratios. Strings remain resources; the reusable color palette lives in the shared source-level `UiTheme` helper because the Connect IQ resource schema does not define standalone reusable color resources. Screen geometry and dummy state do not live in resources.

Views calculate geometry outside the hot drawing path and set the managed layout before interaction. `onUpdate()` only clears and draws prepared state plus the managed drawables. Text wrapping and row counts are bounded to the supplied short fixtures.

Alternative considered: per-device XML layouts would provide fixed placements but duplicate nearly every screen and make future product expansion expensive.

### 5. Route buttons and touch through `Selectable`

Screen delegates will subclass `WatchUi.BehaviorDelegate`. Interactive controls and rows will use `WatchUi.Button`/`Selectable`, and the view will enable `setKeyToSelectableInteraction(true)` so Garmin's current selectable system coordinates physical focus and touch selection. `SelectableEvent` and behavior callbacks will resolve to the same `activate(actionId)` method, so input types cannot diverge in navigation or state effects.

Multi-action screens expose a visible highlighted `Selectable`. Garmin's selectable interaction moves physical focus and dispatches touch selection; Select activates the focused object. Back, menu, and page behaviors remain in the delegate. The complete flow must work without touch on fēnix 7X, while touch is the primary path on Edge 1040. The input design follows Garmin's current [`Selectable` input model](https://developer.garmin.com/connect-iq/core-topics/input-handling/) rather than maintaining independent raw-key and tap hit-test systems.

Alternative considered: separate touch and button delegates would simplify individual handlers but duplicate action mapping and increase parity defects.

### 6. Organize the scaffold by responsibility

The initial structure will follow repository guidance while staying proportional to this foreground-only change:

```text
manifest.xml
monkey.jungle
resources/
  drawables/          # application launcher icon only
  menus/              # resource-defined native Menu2 destination menu
  strings/            # labels and user-visible dummy text
source/
  WristLinkApp.mc
  model/              # DemoData and DemoSession
  navigation/         # AppNavigator and menu delegate
  ui/                 # shared source-defined color theme, geometry, drawing, base delegate helpers
  screens/            # Home, Recent, Saved Notes, Status, About, received views
tests/
  model/              # deterministic session-transition tests
  navigation/         # semantic action/route tests where SDK test support allows
```

Messaging, payload, and storage directories will not be added as empty placeholders. They should appear only when those capabilities are implemented.

If a layout cannot remain legible through shared geometry, add the narrowest justified resource override (`resources-round/` or `resources-rectangle/`) rather than branching screen logic by device. Device-specific resource roots are a last resort, and device and family qualifiers must not be combined in one directory name.

### 7. Verify with compile, state, input, and visual matrices

Implementation verification will include:

- warning-enabled compile at minimum API 5.2.0 for both `fenix7x` and `edge1040` using an external `$CONNECTIQ_KEY`;
- Monkey C unit tests for deterministic `DemoSession` transitions;
- simulator walkthrough of every required route without touch on `fenix7x`;
- touch walkthrough of every required route on `edge1040`, plus touch-parity checks on `fenix7x`;
- compiler review confirming all referenced Toybox types and options exist at API 5.2.0 and no deprecated API warning is emitted;
- screenshot inspection against `docs/design/paper`, checking hierarchy, theme, clipping, focus, and readable primary actions rather than pixel identity;
- a source check confirming no Communications, Background, or Application.Storage integration was introduced.

The Paper files are not changed by this implementation, so their PNG snapshots do not require regeneration.

## Risks / Trade-offs

- **[Paper layouts are primarily round and do not prescribe every aspect ratio]** → Use safe-area-aware geometry, test a rectangular target explicitly, and preserve hierarchy before decorative spacing.
- **[Native Menu2 appearance will differ from the illustrative Paper menu]** → Treat item order and destinations as the contract and accept Garmin's device-specific native chrome.
- **[Dummy Connected/Acknowledged values could be mistaken for live transport state]** → Keep all values in the named demo fixture provider and ensure no communications APIs are present, making later replacement localized and auditable.
- **[Inline local outcomes add states not shown in Paper]** → Keep outcomes minimal and reuse existing screen chrome so buttons are demonstrably functional without expanding the product flow.
- **[Selectable focus or touch behavior can differ between watch and Edge device families]** → Use Garmin-managed `Selectable` layouts, keep semantic activation centralized, and exercise both simulator profiles.
- **[A narrow initial product list limits installability]** → Expand manifest support only after compiling and visually checking additional representative devices.
- **[API 5.2.0 intentionally excludes older firmware and product families]** → Keep the baseline explicit and treat compatibility expansion as a separately verified change.
- **[The new UUID will become a cross-project contract]** → Generate it once, commit it in the manifest, display the stable identity in About, and call out any future change as coordinated breaking work.

## Migration Plan

This is an additive initial scaffold with no runtime data to migrate.

1. Add the manifest, stable UUID, canonical `monkey.jungle`, resources, and launcher icon with only the two verified products and no permissions.
2. Add the session model and tests before screens so local state transitions are independently verifiable.
3. Add shared UI/input utilities, the navigator and native menu, then the required screens in navigation order.
4. Compile and run the complete walkthrough on both simulator targets and correct warnings or clipping before broadening support.

Rollback is removal of the newly added Connect IQ scaffold files. No user state, external registration, or protocol revision needs rollback.
